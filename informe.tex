\section*{RESUMEN}

Los estudiantes de Ingeniería de Sistemas enfrentan dificultades para comprender el análisis léxico y sintáctico de compiladores, ya que estos conceptos suelen enseñarse sin herramientas visuales que permitan observar la tokenización y construcción de árboles sintácticos en tiempo real. El presente proyecto aborda esta problemática mediante el desarrollo de un analizador léxico y sintáctico multilenguaje con validación semántica y cálculo de entropía de Shannon. La herramienta soporta cinco lenguajes de programación (C, C++, Java, JavaScript y Python) cada uno con su propio lexer, parser, validador semántico y AST diferenciado. La arquitectura del sistema se basa en los cuatro pilares de la Programación Orientada a Objetos (abstracción, herencia, polimorfismo y encapsulamiento) implementados mediante un patrón Factory que selecciona dinámicamente el analizador adecuado según el lenguaje. El backend está construido con Flask (Python) organizado en tres capas (routes → services → core), mientras que el frontend ofrece un editor inteligente con resaltado sintáctico, autocompletado y visualización interactiva de tokens, AST, validación semántica y estadísticas de entropía. Cuenta con 50 pruebas unitarias y de integración HTTP, todas ejecutadas exitosamente, y está contenedorizado con Docker para garantizar portabilidad.

\textbf{Palabras clave:} análisis léxico, análisis sintáctico, AST, multilenguaje, POO, entropía de Shannon, compiladores, ingeniería de software.

\section*{ABSTRACT}

Systems Engineering students face difficulties in understanding the lexical and syntactic analysis of compilers, as these concepts are usually taught without visual tools that allow observing tokenization and syntax tree construction in real time. This project addresses this problem through the development of a multi-language lexical and syntactic analyzer with semantic validation and Shannon entropy calculation. The tool supports five programming languages (C, C++, Java, JavaScript and Python) each with its own lexer, parser, semantic validator and differentiated AST. The system architecture is based on the four pillars of Object-Oriented Programming implemented through a Factory Pattern that dynamically selects the appropriate analyzer based on the language. The backend is built with Flask (Python) organized in three layers (routes, services, core), while the frontend offers an intelligent editor with syntax highlighting and interactive visualization of tokens, AST, semantic validation and entropy statistics. The system includes 50 unit and HTTP integration tests, all successfully executed, and is containerized with Docker to ensure portability.

\textbf{Keywords:} lexical analysis, syntactic analysis, AST, multi-language, OOP, Shannon entropy, compilers, software engineering.

\section{INTRODUCCIÓN}

En la formación de estudiantes de Ingeniería de Sistemas, la comprensión de los procesos internos de un compilador constituye un pilar fundamental del curso de Lenguajes de Programación. Sin embargo, el análisis léxico y sintáctico suele enseñarse de manera predominantemente teórica, lo que genera una brecha significativa entre los conceptos abstractos y su aplicación práctica \cite{aho2012}.

Cuando un estudiante escribe un programa en C, Java o Python, rara vez se detiene a pensar cómo el compilador o intérprete descompone ese código en tokens, construye un árbol sintáctico y valida reglas semánticas. Esta desconexión limita la profundidad del aprendizaje y dificulta la comprensión de por qué ciertos errores son detectados en tiempo de compilación y otros en tiempo de ejecución.

El presente proyecto aborda esta problemática mediante el desarrollo de una herramienta interactiva que permite visualizar, en tiempo real, el proceso completo de análisis de código fuente. A diferencia de las herramientas tradicionales que se limitan a un solo lenguaje, este sistema soporta cinco lenguajes distintos, cada uno con reglas léxicas, sintácticas y semánticas propias, ofreciendo una experiencia de aprendizaje comparativa.

El sistema se complementa con el cálculo de la entropía de Shannon aplicada a la distribución de tokens, lo que añade una dimensión cuantitativa al análisis: permite medir la complejidad informativa del código fuente y comparar cómo una misma operación (por ejemplo, una función) presenta distinta diversidad léxica según el lenguaje en que se escribe \cite{shannon1948}.

La arquitectura del software se diseñó siguiendo principios de ingeniería de software: separación en capas, uso de patrones de diseño (Factory Pattern) y aplicación estricta de los cuatro pilares de la Programación Orientada a Objetos. Esto garantiza que el sistema no solo sea funcional, sino también mantenible, extensible y didáctico en su estructura interna.

\section{PLANTEAMIENTO DEL PROBLEMA}

\subsection{Problema central}

¿Cómo se puede desarrollar una herramienta interactiva que reconozca las partes de un código fuente en múltiples lenguajes de programación y ayude a entender el funcionamiento interno de un compilador, aplicando principios de ingeniería de software?

\subsection{Problemas específicos}

\begin{enumerate}[label=\textbf{P\arabic*:}]
    \item Los analizadores existentes se enfocan en un solo lenguaje, lo que impide la comparación entre distintos paradigmas sintácticos.
    \item La teoría de compiladores se enseña sin una herramienta visual que muestre tokens, AST y validación semántica en tiempo real.
    \item La complejidad informativa del código fuente rara vez se cuantifica, perdiendo la oportunidad de aplicar teoría de la información al análisis de programas.
    \item La mayoría de proyectos académicos carecen de una arquitectura de software bien definida, dificultando su escalabilidad y mantenimiento.
\end{enumerate}

\section{JUSTIFICACIÓN}

El proyecto se justifica desde tres dimensiones:

\textbf{Dimensión académica:} Proporciona un recurso didáctico que transforma conceptos abstractos de compiladores en visualizaciones concretas. El estudiante puede ver cómo un \texttt{for} en C genera tokens distintos a un \texttt{for...in} en Python, o cómo una clase en Java produce un AST radicalmente diferente al de una función en JavaScript.

\textbf{Dimensión técnica:} Aplica principios de ingeniería de software, arquitectura en capas, patrones de diseño y POO que son exigidos en el perfil profesional del ingeniero de sistemas. El sistema es escalable: agregar un nuevo lenguaje requiere solo crear un nuevo módulo sin modificar el código existente.

\textbf{Dimensión investigativa:} Introduce la entropía de Shannon como métrica de complejidad léxica, abriendo una línea de análisis cuantitativo sobre código fuente que complementa el análisis cualitativo tradicional.

\subsection{Fase 3: Diseño orientado a objetos -- Los 4 pilares de POO}

El sistema aplica rigurosamente los cuatro pilares de la Programación Orientada a Objetos, distribuidos de la siguiente manera:

\subsubsection{Abstracción}

Se definieron clases abstractas base que establecen \textbf{qué} debe hacer cada componente, sin especificar \textbf{cómo}:

\begin{itemize}
    \item \texttt{TokenBase}: define los atributos comunes de cualquier token (valor, línea, columna).
    \item \texttt{AnalizadorLexicoBase}: interfaz abstracta con el método \texttt{analizar()} que todo lexer debe implementar.
    \item \texttt{ParserBase}: interfaz abstracta con el método \texttt{analizar()} que todo parser debe implementar.
    \item \texttt{ValidadorSemanticoBase}: clase abstracta con lógica de ámbitos compartida y método \texttt{validar()}.
\end{itemize}

\subsubsection{Herencia}

Se estableció una jerarquía de dos niveles para los lenguajes de sintaxis C-like:

\begin{itemize}
    \item \texttt{CLikeLexerBase} hereda de \texttt{AnalizadorLexicoBase} y proporciona lógica común de tokenización con expresiones regulares.
    \item \texttt{CLikeParserBase} hereda de \texttt{ParserBase} y proporciona métodos compartidos para parsear \texttt{if}, \texttt{while}, \texttt{for}, \texttt{return}, expresiones y bloques.
    \item Los lexers de C, C++, Java y JavaScript heredan de \texttt{CLikeLexerBase}, reutilizando toda la lógica de regex.
    \item Los parsers de C, C++, Java y JavaScript heredan de \texttt{CLikeParserBase} y sobrescriben \texttt{sentencia()} con reglas específicas.
    \item Python hereda directamente de las clases base abstractas porque su sintaxis basada en indentación es radicalmente distinta.
\end{itemize}

\subsubsection{Polimorfismo}

El polimorfismo se manifiesta en múltiples niveles:

\begin{itemize}
    \item \texttt{sentencia()} tiene implementaciones distintas en cada parser: CParser reconoce tipos C, CppParser agrega clases y namespace, JavaParser exige clases como toplevel, JavaScriptParser maneja \texttt{var/let/const} y arrow functions, PythonParser maneja indentación.
    \item \texttt{validar()} se comporta distinto según el lenguaje: el validador de Python trata \texttt{asignacion} como declaración (tipado dinámico), mientras que el de C exige declaración explícita de tipos.
    \item \texttt{get\_analizador(lenguaje)} y \texttt{get\_validador\_semantico(lenguaje, ast)} retornan instancias de clases distintas pero con la misma interfaz.
\end{itemize}

\subsubsection{Encapsulamiento}

\begin{itemize}
    \item Los métodos privados de los lexers (\texttt{\_crear\_token}, \texttt{\_manejar\_espacios}, \texttt{\_procesar\_indentacion}) ocultan la complejidad interna.
    \item La configuración del sistema se centraliza en \texttt{config.py}, exponiendo solo constantes.
    \item El Factory oculta qué clases concretas se instancian; el cliente solo pide por nombre de lenguaje.
    \item El servicio \texttt{ServicioAnalisis} encapsula toda la lógica de negocio; las rutas HTTP solo manejan request/response.
\end{itemize}

\subsection{Fase 6: Flujo de procesamiento}

El flujo completo de análisis de un fragmento de código sigue la siguiente secuencia:

\begin{enumerate}
    \item El frontend envía el código y el lenguaje seleccionado al endpoint \texttt{POST /analizar}.
    \item La ruta HTTP delega en el \texttt{ServicioAnalisis}.
    \item El Factory retorna el \texttt{AnalizadorLenguaje} correspondiente.
    \item El lexer específico tokeniza el código usando expresiones regulares propias del lenguaje.
    \item El parser específico consume los tokens y construye un AST mediante descenso recursivo.
    \item El validador semántico específico recorre el AST verificando scope, declaraciones y tipos.
    \item El calculador de entropía procesa la distribución de tokens y genera estadísticas.
    \item El resultado se empaqueta en JSON y se retorna al frontend para su visualización.
\end{enumerate}

\subsection{Entropía de Shannon aplicada a tokens}

La entropía de Shannon se calcula sobre la distribución de frecuencias de los tipos de token. La fórmula aplicada es:

\[ H = -\sum_{i=1}^{n} p_i \log_2(p_i) \]

Donde \( p_i \) es la probabilidad del tipo de token \( i \) y \( n \) es el número de tipos únicos. La entropía se normaliza dividiendo por la entropía máxima \( H_{max} = \log_2(n) \), obteniendo un valor entre 0 y 1.

La Tabla \ref{tab:entropia} muestra la entropía calculada para una misma función implementada en cada lenguaje.

\begin{table}[H]
\centering
\small
\caption{Entropía de Shannon para una función de suma en cada lenguaje}
\label{tab:entropia}
\begin{tabular}{@{}lccc@{}}
\toprule
\textbf{Lenguaje} & \textbf{Total tokens} & \textbf{Tipos únicos} & \textbf{Entropía normalizada} \\
\midrule
C & 14 & 10 & 0.92 \\
C++ & 14 & 10 & 0.92 \\
Java & 16 & 10 & 0.87 \\
JavaScript (arrow) & 12 & 9 & 0.94 \\
Python & 10 & 8 & 0.95 \\
\bottomrule
\end{tabular}
\end{table}

Se observa que Python tiene la menor cantidad de tokens pero la mayor entropía normalizada, lo que indica una distribución más uniforme de tipos de token (mayor diversidad léxica relativa). Java, al requerir más tokens para la misma operación, presenta una entropía normalizada menor.

\begin{figure}[H]

    \imgstd{resultado_entropia.png}

La entropía de Shannon demuestra ser una métrica útil para cuantificar diferencias que el análisis cualitativo solo puede describir. La misma función de suma produce una entropía normalizada de 0.95 en Python pero 0.87 en Java, lo que refleja matemáticamente la verbosidad sintáctica de Java frente a la concisión de Python. Esta cuantificación permite comparar lenguajes de forma objetiva, midiendo la diversidad léxica relativa de cada uno.

Los resultados obtenidos confirman que es posible construir un analizador multilenguaje con identidad propia para cada lenguaje, manteniendo una arquitectura modular y extensible. El uso de los cuatro pilares de POO no fue un requisito meramente académico, sino una necesidad arquitectónica real: sin herencia, los cuatro lenguajes C-like habrían requerido código duplicado; sin polimorfismo, el Factory no podría seleccionar dinámicamente el analizador correcto; sin abstracción, no existiría una interfaz común que permita tratar a todos los analizadores de manera uniforme; sin encapsulamiento, los detalles internos de cada lexer y parser contaminarían las capas superiores.

Entre las limitaciones identificadas se encuentran: el type checking es básico y no cubre expresiones compuestas ni tipos definidos por el usuario; los parsers no soportan constructos avanzados como \texttt{switch/case}, \texttt{do-while} o \texttt{try/except}; la detección de lenguaje automática es probabilística y puede fallar con código ambiguo; y el frontend depende de CDN para Bootstrap y CodeMirror, lo que requiere conexión a Internet.

\section{CONCLUSIONES}

\begin{enumerate}[label=\textbf{\arabic*.}]
    \item Se desarrolló exitosamente un analizador léxico y sintáctico que soporta cinco lenguajes de programación con tokens, AST y reglas semánticas propias para cada uno, demostrando que la arquitectura orientada a objetos con Factory Pattern permite escalar de un lenguaje a múltiples sin reescribir el núcleo del sistema.

    \item La aplicación de los cuatro pilares de POO (abstracción, herencia, polimorfismo y encapsulamiento) no solo cumplió con los requisitos académicos, sino que resultó en un código mantenible donde agregar un nuevo lenguaje requiere únicamente crear una nueva clase que herede de las bases existentes.

    \item La arquitectura en tres capas (routes → services → core) separó efectivamente las responsabilidades del sistema: las rutas manejan HTTP, los servicios orquestan la lógica, y el core contiene los analizadores. Esta separación facilitó las pruebas unitarias y de integración.

    \item El cálculo de entropía de Shannon sobre tokens demostró ser una métrica efectiva para cuantificar la complejidad léxica del código, permitiendo comparaciones objetivas entre lenguajes. La misma operación produce distinta entropía según la verbosidad sintáctica del lenguaje.

    \item Las 50 pruebas automatizadas (unitarias + integración HTTP) garantizan la confiabilidad del sistema y sirven como documentación ejecutable de cada funcionalidad implementada.

    \item La interfaz web con editor CodeMirror, panel de entropía y tabla comparativa proporciona una experiencia de aprendizaje interactiva que transforma conceptos abstractos de compiladores en visualizaciones concretas y comparables.
\end{enumerate}
