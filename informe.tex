\section*{RESUMEN}
\addcontentsline{toc}{section}{RESUMEN}

El presente proyecto consiste en el desarrollo de un analizador léxico y sintáctico multilenguaje con validación semántica y cálculo de entropía de Shannon. La herramienta soporta cinco lenguajes de programación (C, C++, Java, JavaScript y Python) cada uno con su propio lexer, parser, validador semántico y AST diferenciado. La arquitectura del sistema se basa en los cuatro pilares de la Programación Orientada a Objetos (abstracción, herencia, polimorfismo y encapsulamiento) implementados mediante un patrón Factory que selecciona dinámicamente el analizador adecuado según el lenguaje. El backend está construido con Flask (Python) organizado en tres capas (routes → services → core), mientras que el frontend ofrece un editor inteligente con resaltado sintáctico, autocompletado y visualización interactiva de tokens, AST, validación semántica y estadísticas de entropía. El sistema integra la Programación Funcional (tres pilares: pureza, inmutabilidad y composición) junto con POO en un diseño de doble paradigma. Cuenta con 68 pruebas unitarias, de integración HTTP y funcionales, todas ejecutadas exitosamente, y está contenedorizado con Docker para garantizar portabilidad.

\textbf{Palabras clave:} análisis léxico, análisis sintáctico, AST, multilenguaje, POO, entropía de Shannon, compiladores, ingeniería de software.

\section*{ABSTRACT}
\addcontentsline{toc}{section}{ABSTRACT}

This project consists of the development of a multi-language lexical and syntactic analyzer with semantic validation and Shannon entropy calculation. The tool supports five programming languages (C, C++, Java, JavaScript and Python) each with its own lexer, parser, semantic validator and differentiated AST. The system architecture is based on the four pillars of Object-Oriented Programming (abstraction, inheritance, polymorphism and encapsulation) implemented through a Factory Pattern that dynamically selects the appropriate analyzer based on the language. The backend is built with Flask (Python) organized in three layers (routes → services → core), while the frontend offers an intelligent editor with syntax highlighting, autocompletion and interactive visualization of tokens, AST, semantic validation and entropy statistics. The system includes 50 unit and HTTP integration tests, all successfully executed, and is containerized with Docker to ensure portability.

\textbf{Keywords:} lexical analysis, syntactic analysis, AST, multi-language, OOP, Shannon entropy, compilers, software engineering.

\section{INTRODUCCIÓN}

En la formación de estudiantes de Ingeniería de Sistemas, la comprensión de los procesos internos de un compilador constituye un pilar fundamental del curso de Lenguajes de Programación. Sin embargo, el análisis léxico y sintáctico suele enseñarse de manera predominantemente teórica, lo que genera una brecha significativa entre los conceptos abstractos y su aplicación práctica \cite{aho2012}.

Cuando un estudiante escribe un programa en C, Java o Python, rara vez se detiene a pensar cómo el compilador o intérprete descompone ese código en tokens, construye un árbol sintáctico y valida reglas semánticas. Esta desconexión limita la profundidad del aprendizaje y dificulta la comprensión de por qué ciertos errores son detectados en tiempo de compilación y otros en tiempo de ejecución.

El presente proyecto aborda esta problemática mediante el desarrollo de una herramienta interactiva que permite visualizar, en tiempo real, el proceso completo de análisis de código fuente. A diferencia de las herramientas tradicionales que se limitan a un solo lenguaje, este sistema soporta cinco lenguajes distintos, cada uno con reglas léxicas, sintácticas y semánticas propias, ofreciendo una experiencia de aprendizaje comparativa.

El sistema se complementa con el cálculo de la entropía de Shannon aplicada a la distribución de tokens, lo que añade una dimensión cuantitativa al análisis: permite medir la complejidad informativa del código fuente y comparar cómo una misma operación (por ejemplo, una función) presenta distinta diversidad léxica según el lenguaje en que se escribe \cite{shannon1948}.

La arquitectura del software se diseñó siguiendo principios de ingeniería de software: separación en capas, uso de patrones de diseño (Factory Pattern) y aplicación estricta de los cuatro pilares de la Programación Orientada a Objetos. Esto garantiza que el sistema no solo sea funcional, sino también mantenible, extensible y didáctico en su estructura interna.

\section{PLANTEAMIENTO DEL PROBLEMA}

\subsection{Problema central}

¿Cómo se puede desarrollar una herramienta interactiva que reconozca las partes de un código fuente en múltiples lenguajes de programación y ayude a entender el funcionamiento interno de un compilador, aplicando principios de ingeniería de software?

\subsection{Problemas específicos}

\begin{enumerate}[label=\textbf{P\arabic*:}]
    \item Los analizadores existentes se enfocan en un solo lenguaje, lo que impide la comparación entre distintos paradigmas sintácticos.
    \item La teoría de compiladores se enseña sin una herramienta visual que muestre tokens, AST y validación semántica en tiempo real.
    \item La complejidad informativa del código fuente rara vez se cuantifica, perdiendo la oportunidad de aplicar teoría de la información al análisis de programas.
    \item La mayoría de proyectos académicos carecen de una arquitectura de software bien definida, dificultando su escalabilidad y mantenimiento.
\end{enumerate}

\section{JUSTIFICACIÓN}

El proyecto se justifica desde tres dimensiones:

\textbf{Dimensión académica:} Proporciona un recurso didáctico que transforma conceptos abstractos de compiladores en visualizaciones concretas. El estudiante puede ver cómo un \texttt{for} en C genera tokens distintos a un \texttt{for...in} en Python, o cómo una clase en Java produce un AST radicalmente diferente al de una función en JavaScript.

\textbf{Dimensión técnica:} Aplica principios de ingeniería de software, arquitectura en capas, patrones de diseño y POO que son exigidos en el perfil profesional del ingeniero de sistemas. El sistema es escalable: agregar un nuevo lenguaje requiere solo crear un nuevo módulo sin modificar el código existente.

\textbf{Dimensión investigativa:} Introduce la entropía de Shannon como métrica de complejidad léxica, abriendo una línea de análisis cuantitativo sobre código fuente que complementa el análisis cualitativo tradicional.

\section{OBJETIVOS}

\subsection{Objetivo general}

Desarrollar un analizador léxico y sintáctico multilenguaje con validación semántica, aplicando arquitectura en capas, los cuatro pilares de la Programación Orientada a Objetos y la teoría de la información de Shannon.

\subsection{Objetivos específicos}

\begin{enumerate}[label=\textbf{O\arabic*:}]
    \item Identificar tokens con reglas léxicas diferenciadas para C, C++, Java, JavaScript y Python, incluyendo palabras reservadas, operadores compuestos y símbolos propios de cada lenguaje.
    \item Construir parsers independientes por lenguaje que generen árboles sintácticos (AST) con estructuras específicas: clases en Java/C++, funciones flecha en JavaScript, indentación en Python.
    \item Implementar validadores semánticos con reglas propias por lenguaje: scope de variables, type checking básico y detección de asignaciones incompatibles.
    \item Calcular la entropía de Shannon sobre la distribución de tokens para medir la complejidad informativa del código fuente y comparar entre lenguajes.
    \item Diseñar una interfaz web con editor inteligente (CodeMirror) que ofrezca resaltado sintáctico, autocompletado, visualización de AST y estadísticas de entropía.
\end{enumerate}

\subsection{Fase 3: Diseño orientado a objetos -- Los 4 pilares de POO}

El sistema aplica rigurosamente los cuatro pilares de la Programación Orientada a Objetos, distribuidos de la siguiente manera:

\subsubsection{Abstracción}

Se definieron clases abstractas base que establecen \textbf{qué} debe hacer cada componente, sin especificar \textbf{cómo}:

\begin{itemize}
    \item \texttt{TokenBase}: define los atributos comunes de cualquier token (valor, línea, columna).
    \item \texttt{AnalizadorLexicoBase}: interfaz abstracta con el método \texttt{analizar()} que todo lexer debe implementar.
    \item \texttt{ParserBase}: interfaz abstracta con el método \texttt{analizar()} que todo parser debe implementar.
    \item \texttt{ValidadorSemanticoBase}: clase abstracta con lógica de ámbitos compartida y método \texttt{validar()}.
\end{itemize}

\subsubsection{Herencia}

Se estableció una jerarquía de dos niveles para los lenguajes de sintaxis C-like:

\begin{itemize}
    \item \texttt{CLikeLexerBase} hereda de \texttt{AnalizadorLexicoBase} y proporciona lógica común de tokenización con expresiones regulares.
    \item \texttt{CLikeParserBase} hereda de \texttt{ParserBase} y proporciona métodos compartidos para parsear \texttt{if}, \texttt{while}, \texttt{for}, \texttt{return}, expresiones y bloques.
    \item Los lexers de C, C++, Java y JavaScript heredan de \texttt{CLikeLexerBase}, reutilizando toda la lógica de regex.
    \item Los parsers de C, C++, Java y JavaScript heredan de \texttt{CLikeParserBase} y sobrescriben \texttt{sentencia()} con reglas específicas.
    \item Python hereda directamente de las clases base abstractas porque su sintaxis basada en indentación es radicalmente distinta.
\end{itemize}

\subsubsection{Polimorfismo}

El polimorfismo se manifiesta en múltiples niveles:

\begin{itemize}
    \item \texttt{sentencia()} tiene implementaciones distintas en cada parser: CParser reconoce tipos C, CppParser agrega clases y namespace, JavaParser exige clases como toplevel, JavaScriptParser maneja \texttt{var/let/const} y arrow functions, PythonParser maneja indentación.
    \item \texttt{validar()} se comporta distinto según el lenguaje: el validador de Python trata \texttt{asignacion} como declaración (tipado dinámico), mientras que el de C exige declaración explícita de tipos.
    \item \texttt{get\_analizador(lenguaje)} y \texttt{get\_validador\_semantico(lenguaje, ast)} retornan instancias de clases distintas pero con la misma interfaz.
\end{itemize}

\subsubsection{Encapsulamiento}

\begin{itemize}
    \item Los métodos privados de los lexers (\texttt{\_crear\_token}, \texttt{\_manejar\_espacios}, \texttt{\_procesar\_indentacion}) ocultan la complejidad interna.
    \item La configuración del sistema se centraliza en \texttt{config.py}, exponiendo solo constantes.
    \item El Factory oculta qué clases concretas se instancian; el cliente solo pide por nombre de lenguaje.
    \item El servicio \texttt{ServicioAnalisis} encapsula toda la lógica de negocio; las rutas HTTP solo manejan request/response.
\end{itemize}

\subsection{Fase 6: Flujo de procesamiento}

El flujo completo de análisis de un fragmento de código sigue la siguiente secuencia:

\begin{enumerate}
    \item El frontend envía el código y el lenguaje seleccionado al endpoint \texttt{POST /analizar}.
    \item La ruta HTTP delega en el \texttt{ServicioAnalisis}.
    \item El Factory retorna el \texttt{AnalizadorLenguaje} correspondiente.
    \item El lexer específico tokeniza el código usando expresiones regulares propias del lenguaje.
    \item El parser específico consume los tokens y construye un AST mediante descenso recursivo.
    \item El validador semántico específico recorre el AST verificando scope, declaraciones y tipos.
    \item El calculador de entropía procesa la distribución de tokens y genera estadísticas.
    \item El resultado se empaqueta en JSON y se retorna al frontend para su visualización.
\end{enumerate}

\subsection{Fase 7: Programación Funcional -- Los 3 Pilares}

Además del paradigma orientado a objetos, el proyecto incorpora los tres pilares fundamentales de la Programación Funcional (FP): \textbf{pureza}, \textbf{inmutabilidad} y \textbf{composición}. Estos pilares no compiten con POO, sino que la complementan en componentes específicos donde la predictibilidad matemática y la ausencia de efectos secundarios ofrecen ventajas de robustez.

\subsubsection{Pilar 1: Funciones Puras}

Una función pura es aquella que cumple dos propiedades estrictas:

\begin{enumerate}
    \item \textbf{Determinismo}: Para los mismos argumentos de entrada, siempre retorna el mismo resultado.
    \item \textbf{Aislamiento}: No produce efectos secundarios (no modifica variables externas, no escribe archivos, no imprime en consola, no lanza excepciones).
\end{enumerate}

En el proyecto, las funciones puras se concentran en el módulo \texttt{core/funcional.py} y se aplican en los siguientes componentes:

\begin{itemize}
    \item \texttt{calcular\_entropia\_pura(tipos\_tokens)}: Recibe una tupla de tipos de token y retorna un diccionario con entropía, entropía máxima, normalización, total, tipos únicos, densidad y distribución. No depende de ningún estado externo; dado el mismo input, produce el mismo output siempre (Figura \ref{fig:fp_pureza}).
    
    \item \texttt{map\_puro(fn, iterable)}: Aplica una función a cada elemento de una secuencia y retorna una tupla inmutable. Equivalente funcional de \texttt{map()}.
    
    \item \texttt{filter\_puro(fn, iterable)}: Filtra elementos según un predicado y retorna una tupla inmutable.
    
    \item \texttt{reduce\_puro(fn, iterable, inicial)}: Acumula valores aplicando una función binaria, sin mutar estado externo.
    
    \item \texttt{composicion(*funcs)}: Compone múltiples funciones en una tubería (\textit{pipeline}) donde la salida de una es la entrada de la siguiente: \texttt{composicion(f, g, h)(x) = h(g(f(x)))}.
\end{itemize}

La Tabla \ref{tab:fp_vs_oop} contrasta el enfoque OOP (estado mutable encapsulado) con el enfoque FP (funciones puras sin estado) para el mismo cálculo de entropía.

\begin{table}[H]
\centering
\small
\caption{Doble paradigma: OOP vs Funcional para el cálculo de entropía}
\label{tab:fp_vs_oop}
\begin{tabular}{@{}p{5.2cm}p{5.2cm}@{}}
\toprule
\textbf{Enfoque OOP (CalculadorEntropia)} & \textbf{Enfoque FP (calcular\_entropia\_pura)} \\
\midrule
Instancia con estado interno mutable (self.tokens, self.frecuencias). & Función sin estado: recibe datos, retorna resultados. \\
\addlinespace
Métodos consultan el estado acumulado (self.total, self.calcular()). & Cada llamada es independiente; no comparte ni modifica estado. \\
\addlinespace
Útil cuando se necesitan múltiples consultas sobre el mismo conjunto de tokens. & Útil para cálculos aislados, comparaciones entre lenguajes y testing. \\
\bottomrule
\end{tabular}
\end{table}

Ambos enfoques producen resultados idénticos, lo cual fue verificado mediante la prueba \texttt{test\_fp\_equivalencia\_oop\_vs\_funcional} (68 pruebas, 0 fallos).

\subsubsection{Pilar 2: Inmutabilidad}

La inmutabilidad establece que una vez que un dato es creado, no puede ser modificado. Cualquier ``cambio'' implica crear una nueva copia con la modificación deseada, dejando el original intacto. Esto elimina condiciones de carrera y hace el código \textit{thread-safe} por naturaleza.

En Python, la inmutabilidad se implementa mediante:

\begin{itemize}
    \item \textbf{Tuplas} en lugar de listas para colecciones que no deben cambiar.
    \item \textbf{@dataclass(frozen=True)} para objetos cuyos atributos son fijos tras la construcción.
    \item \textbf{MappingProxyType} para diccionarios de solo lectura.
    \item \textbf{replace()} de \texttt{dataclasses} para crear copias con campos modificados sin mutar el original.
\end{itemize}

\subsubsection{Pilar 3: Composición Funcional}

La composición funcional consiste en unir funciones como piezas de LEGO, donde la salida de una función se convierte en la entrada de la siguiente. El software se transforma en una serie de tuberías (\textit{pipelines}) conectadas por donde fluyen los datos sin ser destruidos.

En el proyecto, la función \texttt{composicion(*funcs)} implementa este principio:

\begin{verbatim}
composicion(f, g, h)(x) = h(g(f(x)))
\end{verbatim}

Esto permite construir cadenas de procesamiento declarativas, donde cada paso es una función pura que transforma los datos sin efectos secundarios:

\begin{verbatim}
pipeline = composicion(
    transformar_tokens_a_tipos,   # Paso 1: extraer tipos
    calcular_entropia_pura,       # Paso 2: calcular entropía
)
resultado = pipeline(tokens)     # Flujo declarativo
\end{verbatim}

\subsubsection{Conceptos avanzados: Closures}

Un \textbf{closure} es una función interna que ``recuerda'' el valor de una variable externa, incluso después de que la función padre haya terminado su ejecución. Es la forma funcional de tener estado sin usar clases ni variables mutables. En palabras del paradigma: ``Un closure es la forma funcional de un objeto''.

En el proyecto se implementan tres closures:

\begin{itemize}
    \item \texttt{crear\_multiplicador\_token(factor)}: Retorna una función que multiplica frecuencias de tokens por un peso específico. El \texttt{factor} queda ``capturado'' en el scope del closure.
    \item \texttt{crear\_filtro\_por\_tipo(tipo\_objetivo)}: Retorna una función que filtra tokens de un tipo específico. Permite crear filtros especializados sin subclases.
    \item \texttt{crear\_contador\_token()}: Mantiene un estado interno encapsulado (diccionario de conteos) sin usar \texttt{self} ni atributos de clase.
\end{itemize}

\subsubsection{Conceptos avanzados: Decoradores}

Un \textbf{decorador} es una función de orden superior que envuelve a otra para añadirle funcionalidad sin modificar su código fuente. Es ideal para: logs, validaciones, caché y seguridad.

En el proyecto se implementan tres decoradores:

\begin{itemize}
    \item \texttt{@decorador\_pureza}: Valida que la función decorada mantenga su nombre y comportamiento original usando \texttt{@wraps}.
    \item \texttt{@decorador\_validar\_no\_vacio}: Aplica el principio FAIL FAST funcional: si la entrada está vacía, retorna un resultado por defecto sin ejecutar la lógica principal.
    \item \texttt{@decorador\_log}: Registra cada invocación a la función decorada, demostrando el principio de añadir comportamiento sin tocar la lógica interna.
\end{itemize}

\subsubsection{Conceptos avanzados: Partial Application}

La \textbf{aplicación parcial} (\texttt{functools.partial}) permite pre-llenar algunos argumentos de una función, creando un ``atajo'' especializado. Es el equivalente funcional de crear una subclase con valores por defecto, pero sin herencia ni clases:

\begin{verbatim}
duplicar = aplicar_parcial(multiplicar, 2)
duplicar(10)  # 20
\end{verbatim}

\subsubsection{Conceptos avanzados: List Comprehensions}

Las \textbf{list comprehensions} son la forma preferida de Python para combinar map y filter en una sintaxis declarativa y legible:

\begin{verbatim}
[transformacion(x) for x in secuencia if filtro(x)]
\end{verbatim}

En el proyecto, \texttt{filtrar\_y\_transformar\_inmutable()} aplica este patrón retornando tuplas inmutables, combinando la legibilidad de la sintaxis Python con la seguridad de la inmutabilidad funcional.

\subsubsection{Integración de paradigmas: POO + FP}

El proyecto no elige entre POO y FP, sino que los integra donde cada uno aporta mayor valor:

\begin{itemize}
    \item \textbf{POO} gobierna la arquitectura general: clases abstractas, herencia para reutilización, polimorfismo para comportamientos específicos por lenguaje, encapsulamiento para ocultar complejidad.
    \item \textbf{FP} gobierna los cálculos matemáticos y las transformaciones de datos: entropía con funciones puras, map/filter/reduce sobre colecciones, estructuras inmutables para resultados, composición de funciones para pipelines de procesamiento.
\end{itemize}

Esta integración demuestra que los paradigmas no son excluyentes sino complementarios, y que un ingeniero de software debe saber seleccionar la herramienta adecuada para cada componente del sistema.

\subsection{Entropía de Shannon aplicada a tokens}

La entropía de Shannon se calcula sobre la distribución de frecuencias de los tipos de token. La fórmula aplicada es:

\[ H = -\sum_{i=1}^{n} p_i \log_2(p_i) \]

Donde \( p_i \) es la probabilidad del tipo de token \( i \) y \( n \) es el número de tipos únicos. La entropía se normaliza dividiendo por la entropía máxima \( H_{max} = \log_2(n) \), obteniendo un valor entre 0 y 1.

La Tabla \ref{tab:entropia} muestra la entropía calculada para una misma función implementada en cada lenguaje.

\begin{table}[H]

\toprule
\textbf{Lenguaje} & \textbf{Total tokens} & \textbf{Tipos únicos} & \textbf{Entropía normalizada} \\
\midrule

\section{DISCUSIÓN}

Los resultados obtenidos confirman que es posible construir un analizador multilenguaje con identidad propia para cada lenguaje, manteniendo una arquitectura modular y extensible. El uso de los cuatro pilares de POO no fue un requisito meramente académico, sino una necesidad arquitectónica real: sin herencia, los cuatro lenguajes C-like habrían requerido código duplicado; sin polimorfismo, el Factory no podría seleccionar dinámicamente el analizador correcto; sin abstracción, no existiría una interfaz común que permita tratar a todos los analizadores de manera uniforme; sin encapsulamiento, los detalles internos de cada lexer y parser contaminarían las capas superiores.

La incorporación de la entropía de Shannon como métrica complementaria demostró ser útil para cuantificar diferencias que el análisis cualitativo solo puede describir. Por ejemplo, la misma función de suma produce una entropía normalizada de 0.95 en Python pero 0.87 en Java, lo que refleja matemáticamente la verbosidad sintáctica de Java frente a la concisión de Python. El enfoque de doble paradigma (POO + FP) permitió que este cálculo fuera implementado tanto como método de una clase (OOP) como función pura sin estado (FP), verificándose que ambos producen resultados idénticos.

Entre las limitaciones identificadas se encuentran: (1) el type checking es básico y no cubre expresiones compuestas ni tipos definidos por el usuario; (2) los parsers no soportan constructos avanzados como \texttt{switch/case}, \texttt{do-while} o \texttt{try/except}; (3) la detección de lenguaje automática es probabilística y puede fallar con código ambiguo; (4) el frontend depende de CDN para Bootstrap y CodeMirror, lo que requiere conexión a Internet.

\section{CONCLUSIONES}

\begin{enumerate}[label=\textbf{\arabic*.}]
    \item Se desarrolló exitosamente un analizador léxico y sintáctico que soporta cinco lenguajes de programación con tokens, AST y reglas semánticas propias para cada uno, demostrando que la arquitectura orientada a objetos con Factory Pattern permite escalar de un lenguaje a múltiples sin reescribir el núcleo del sistema.

    \item La aplicación de los cuatro pilares de POO (abstracción, herencia, polimorfismo y encapsulamiento) no solo cumplió con los requisitos académicos, sino que resultó en un código mantenible donde agregar un nuevo lenguaje requiere únicamente crear una nueva clase que herede de las bases existentes.

    \item La arquitectura en tres capas (routes → services → core) separó efectivamente las responsabilidades del sistema: las rutas manejan HTTP, los servicios orquestan la lógica, y el core contiene los analizadores. Esta separación facilitó las pruebas unitarias y de integración.

    \item El cálculo de entropía de Shannon sobre tokens demostró ser una métrica efectiva para cuantificar la complejidad léxica del código, permitiendo comparaciones objetivas entre lenguajes. La misma operación produce distinta entropía según la verbosidad sintáctica del lenguaje.

    \item Las 68 pruebas automatizadas (unitarias + integración HTTP + funcionales) garantizan la confiabilidad del sistema y sirven como documentación ejecutable de cada funcionalidad implementada.

    \item La interfaz web con editor CodeMirror, panel de entropía y tabla comparativa proporciona una experiencia de aprendizaje interactiva que transforma conceptos abstractos de compiladores en visualizaciones concretas y comparables.
\end{enumerate}

\subsection{Anexo G: Código fuente del proyecto}

El código fuente completo está disponible en el repositorio GitHub:

\begin{center}
\url{https://github.com/liamcruzticona/LP}
\end{center}

El repositorio incluye:
\begin{itemize}
    \item Código fuente del backend (Python/Flask) con arquitectura en tres capas.
    \item Código fuente del frontend (HTML/CSS/JS) modularizado en 7 archivos.
    \item Archivos de configuración Docker (Dockerfile, docker-compose.yml, nginx.conf).
    \item Suite de 68 pruebas unitarias, de integración y funcionales.
    \item Diagramas UML en formato PlantUML (.puml) e imágenes renderizadas (SVG, PNG).
\end{itemize}

\subsection{Anexo H: Ejecución del proyecto}

Para ejecutar el proyecto en un entorno local:

\begin{enumerate}
    \item Instalar dependencias: \texttt{pip install -r requirements.txt}
    \item Iniciar backend: \texttt{python backend/app.py}
    \item Iniciar frontend: \texttt{python -m http.server 8080 --directory frontend}
    \item Abrir navegador en: \texttt{http://127.0.0.1:8080}
\end{enumerate}

Alternativamente, usando Docker:

\begin{enumerate}
    \item \texttt{docker-compose up --build}
    \item Backend en: \texttt{http://localhost:5000}
    \item Frontend en: \texttt{http://localhost:8080}
\end{enumerate}
